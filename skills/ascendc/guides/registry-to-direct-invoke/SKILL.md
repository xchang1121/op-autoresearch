# Registered Project Migration to Direct-Invoke

Use this skill when the AscendC customizes the operator or registry-invoke project to migrate to the `kernel.py + ascendc_op/` layout.

## 1. Migration principles

Only the registered framework glue is replaced. The Kernel algorithm, the tiling formula and the dtype/shape branch are maintained unless the task expressly requires algorithm rewrite.

## 2. Keep Kernel Logic

Do not change when moving:

- The layout, membership variables, membership functions of the Kernel class.
- Order of `CopyIn`, `Compute`, `CopyOut`, `Process`.
- The helper functions used by the Compute and Data Movement.
- Loop structure, Branch structure and arithmetic expression order.
- dtype-specific path with tilling-key-specific path.

Allowed mechanical modifications:

- Moves include across directories to cost include, or adds a small local dependencies head.
- Adds a namespace to avoid symbol conflicts.
- Replaces the tiling type generated by the framework macro with an equal price for POD script.
- Adjusts the kernel entry ABI to match direct lanch.

## 3. Keep Tiling Formula

The following formulas and branches shall be retained item by item:

- number of cores, tile length, base Shape, alignment, tail calculation.
- With the non-aligned branch.
- dtype, quant, grad, full-load, split-D, etc.
- Molecular/colon sequence, ceil/floor behavior.

Do not try to reduce the number of tiling branches that appear to be similar. Tiling drift is likely to be compiled, but silently miswritten.

## 4. Replace project glue

The glue required for direct-invoke includes:

- Kernel entry: direct launcher for visible parameters.
- Tiling data: host/kernel common common POD regulation.
- Most launch: Calculating tiling, distributing output, moving into stream, starting kernel.
- PyTorch export: Register `torch.ops.npu.<op>` to perform the Meta function.
- `kernel.py`: Lazy load `.so`, call registered operator in `ModelNew.forward()`.

The following registry macros should not be kept in direct-invoke seed:

- `IMPL_OP_OPTILING`
- `REGISTER_TILING_DATA_CLASS`
- runtime `GET_TILING_DATA` dispatch, relying on registry glue
- framework specific `OP_LOG*` macro not available in direct project

The necessary log can be changed to a host side anomaly, debugging `printf` or Python side anomaly; remove the heavy debugging output before final submission.

## 5. Reliance on closed

The current source file for operator recommends copying the entire file. The external public helper only copys the smallest symbol closed:

- SDK include maintains SDK include.
- Small constants and trats can be localized.
- The Helper function must be copied with direct dependence.
- Do not drag large segments into `ascendc_op/`.

After relocation, the following should be checked:

```bash
rg '#include "\\.\\.' ascendc_op
```

The result shall be empty unless the relative include is still in the project tree after copying.

## 6. Host/Device Compile Pass Protection

AscendC `.asc` or `-xasc` compiles may execute host pass and device pass for the same source file. If the head is of the type Divice-only MicroaPI or RegBase, the realization should be protected:

```cpp
#if !defined(__NPU_HOST__)
// device-only kernel implementation
#endif
```

Pure POD tilling header is used both by host and device and should not be covered by the above-mentioned macros.

## 7. Checklist

- The ABI of the host declaration, generated launcher, kernel entire.
- The tensor pointer is passed as `GM_ADDR` or `uint8_t*` according to launcher 's agreement.
- The name, type, sequence, size of the field of tilling string is the same on both sides of the host/kernel.
- PyTorch Meta achieves the correct return of sape and dtype.
- `kernel.py` does not compile, recode or select device at the Import stage.
- `ascendc_op/` and the same grade `kernel.py` constitute the complete task product.
